# shotkit: UX and security audit, 2026-10-17

Asked for by Rock. Every finding below was reproduced in a real browser
against the running app, not inferred from reading code. The commands and
their output are in the session transcript; the numbers here are readings.

---

# Security

## What is already solid

Worth stating first, because it is most of the surface and it is good.

**No XSS, and I tried.** A screenshot was loaded under the filename
`../../<img src=x onerror=alert(1)>‮gnp.exe` + 300 characters. Result:
rendered as a single text node, zero injected elements, no alert. Every
`innerHTML` in `web/` is a static string literal; every piece of user text
reaches the DOM through `textContent` or `setAttribute`.

**Hostile files are rejected at the gate.** An SVG carrying a `<script>`
and a text file disguised as `image/png` were both refused by
`createImageBitmap`, which is the browser's own decoder and the only thing
`web/decode.js` trusts. Neither script ran.

**Nothing leaves the device.** No `fetch`, no `XMLHttpRequest`, no
`sendBeacon`, no WebSocket, no `localStorage`, no cookies, no telemetry.
Screenshots are decoded and composed in the visitor's own browser and never
transmitted.

**Zero runtime dependencies.** `package.json` ships no `dependencies` at
all. There is no third-party JavaScript in the bundle to be compromised.

## S1. No Content-Security-Policy (medium, hardening)

The live site sends `X-Content-Type-Options`, `Referrer-Policy` and
Netlify's own HSTS. It does not send `Content-Security-Policy`,
`Permissions-Policy`, or any `frame-ancestors` / `X-Frame-Options`.

There is no XSS vector today (see above), so this is defence in depth
rather than a live hole. It is still the highest-value header the app is
missing: a CSP would pin script to `'self'`, pin styles and fonts to the
two Google origins the page actually uses, and turn any future injection
from "runs anything" into "blocked". `Permissions-Policy` is free
hardening, because this app needs no camera, microphone or geolocation.

Clickjacking is a real but low-value risk here: there is no account, no
destructive one-click action and nothing to steal, so framing the page
gains an attacker little. Deny it anyway, in the same header block.

## S2. The export filename is attacker-chosen and unsanitised (low)

`sourceStem()` in `web/export.js` strips the path and the extension, which
correctly defuses `../../`. It strips nothing else. Measured, from the
hostile filename above, the string handed to the `download` attribute was:

- **348 characters** long,
- containing `<` and `>`,
- containing **U+202E**, the right-to-left override.

The saved file is still a PNG blob, so the operating system will not
execute it, and a browser sanitises the saved name somewhat. The residual
risk is cosmetic deception: a bidi override can make the name in the
download shelf read as a different extension than the one actually saved.
The realistic path is "someone sends you a screenshot with a crafted name",
not "attacker compromises your machine".

Fix: strip control characters and bidi marks from the stem, and cap its
length. Cheap, and it removes the class rather than the instance.

## S3. Dev dependency vulnerabilities (medium, not user-facing)

`npm audit --omit=dev` reports **0 vulnerabilities**: nothing reaches a
visitor. The full audit reports 4, all in the test toolchain:

| severity | package | issue |
|---|---|---|
| critical | tinypool | prototype pollution in worker options leading to RCE |
| critical | vitest | path traversal / arbitrary file read via `@vitest/mocker` |
| high | source-map-js | event-loop DoS via crafted source-map offsets |
| moderate | @vitest/mocker | the same path traversal |

These are reachable by running the suite against untrusted test files,
which means the dev machine and CI, not the product. They should still be
patched.

## S4. Google Fonts is a third-party dependency (low, privacy)

`web/index.html` loads Inter from `fonts.googleapis.com` and
`fonts.gstatic.com`. Every visitor's IP address and user agent go to
Google, and the page's text rendering depends on Google staying up. The CSS
Google serves cannot execute script, so this is a privacy and availability
issue rather than a code-execution one.

Self-hosting the two Inter weights the app uses removes both, and removes
two preconnects from the critical path.

# UX

## U1. Over the phone limit, files vanish with no word (high)

Reproduced: five portrait screenshots dropped in one go, **three kept, two
discarded, nothing said**. `addFiles` does `.slice(0, MAX_PHONES)` and
returns only decode errors, so a truncation is not an error and never
reaches `showDropErrors`.

The user watches five files go in and three come out. This is the worst
finding in the list, because the app knows exactly what it threw away and
chooses not to mention it.

## U2. A canvas over the browser's limit exports a blank file (high)

Reproduced: typing `50000` into both Custom size fields is accepted,
`render()` returns in **1 ms without throwing**, and the canvas centre pixel
is `[0,0,0,0]` - **completely blank**. Export would hand over that blank
image with no warning.

`applyCustomSize` only rejects values that are negative, zero or
non-finite. It accepted `1e308`.

Browsers cap canvas area at roughly 268 million pixels and any single
dimension at 65535, and exporting at 3x triples each dimension, so the real
ceiling at 1x is about 29 million pixels (5000x5000 is fine; 6000x6000 is
not). Nothing in the app knows this.

The fix is a clamp in `applyCustomSize` AND in `core/config.js normalise`,
which is where that file's own comment says bounded fields are defended, so
a value arriving by any other route is caught too. The number itself is a
product decision: what is the largest canvas shotkit supports?

## U3. Removing a shot by keyboard throws focus away (medium, a11y)

Reproduced: focus the second chip's remove button, activate it, and
`document.activeElement` becomes `<body>`. `renderFileList` rebuilds every
chip on each change, so the focused button is destroyed and nothing takes
its place.

A keyboard user clearing three shots has to Tab from the top of the page
again after each one. Focus should move to the next chip's remove button,
or to Clear when the last one goes.

## U4. Clear is destructive, instant, and cannot be undone (medium)

One click removes every loaded shot. No confirmation, no undo. The shots
are gone and have to be found and dropped again.

The config survives, which was the right call, but that makes the button
feel safer than it is. Either confirm when more than one shot is loaded, or
offer an undo for a few seconds.

## U5. No keyboard way to delete the selected shot (low)

Clicking a shot on the canvas selects it and the right panel edits it, but
Delete and Backspace do nothing. The selection already knows what you mean;
the keyboard does not use it.

## U6. The remove X sat below the labels (fixed in this branch)

`.file-chip` used `align-items: baseline`. A button with no text of its own
has its baseline at its bottom margin edge, so the X hung low. Measured
after the fix: chip, label and X centres all at the same y, off by 0.

## U7. Smaller things, listed not argued

- Phone shots cannot be reordered. Phone 1 is whichever decoded first.
- Dropping a second desktop screenshot replaces the first with no notice.
  Defensible, but it is the same silence as U1 in a smaller place.
- Drop errors announce correctly (`role="alert"`) but cannot be dismissed.
  They clear on the next good drop, so this is minor.

# What I would fix, in order

1. **U2**, the blank export. It ships a wrong file silently, which is worse
   than failing.
2. **U1**, the silent truncation. One sentence of copy.
3. **S1**, the CSP and friends. One block in `netlify.toml`.
4. **U3**, focus after removal. A few lines.
5. **S2**, filename sanitising. A few lines.
6. **U4**, Clear's reversibility. A product decision first.
7. **S4** then **S3**, self-host Inter, patch the dev toolchain.
